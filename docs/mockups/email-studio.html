Mockup — nothing changed The modern interface only (useModernInterface()) · proposed as Administration → Email Studio

Every message this product sends is written in code. Nobody can see it, change it, or choose what is in it without a deployment.

packages/email/src/EmailService.ts is 310 lines: one generic send(), seven template functions that return inline HTML with every colour written into the markup, and eight senders. Every subject is a template literal, the ticket composer's footer is a concatenated paragraph in routes/tickets/index.ts:515, and there is no template table, no template route, and no Email or Templates section among the eight sections of appConfiguration.ts — C7NC & Email holds the connectors, not the copy. The Email Studio is the screen where all of that becomes visible, editable and previewable: a list of every message, an editor in the report designer's idiom, a preview against a real record, a way back, and an explicit choice of what information is sent — kept separate from how it looks.

Every message, subject, sender and caller below was read out of the working copy on 9 October 2026 — the senders and template functions in packages/email/src/EmailService.ts, the callers in services/ticketNotifications.ts, worker.ts, routes/tickets/index.ts, routes/portal.ts, routes/users.ts and routes/auth.ts, the sanitiser in services/emailHtml.ts, the records in seed-full.ts and the report schedule in seed-coverage.ts. Where a message has no sender, or a screen has no history to read, the file says so rather than illustrating one.

Screen one — Messages

Every message, in one list, each row saying what fires it, who reads it, and whether it has been changed

Five groups by what a person is doing when the message goes. Each row carries its stable key, its subject as written in the code, its trigger, its reader, whether it is customer-facing or internal, whether it carries attachments, and its state.

Today, from EmailService.ts: 310 lines, one send(), seven template functions and eight senders. The subjects are template literals (`[${ticketNumber}] …`, `Invoice ${invoiceNumber} — Due ${dueDate}`, "C7NTAX — Your Verification Code"), the bodies are inline HTML with #0f1923 and #c00000 written into them, and the composer's footer is `<hr><p>Ticket: … — …<br>Client: …</p>`. There is no place to look any of it up and no way to change a word of it without a deployment.

Which of these have we changed? Today the honest answer is none of them — not because nobody wanted to, but because there is no way to. The one line that is not decorationa mechanism, not copy

Two sentences in these messages do something rather than say something. They are required blocks: their wording is editable, their presence is not.

In ticket.closure"If this is not resolved, reply to this email — the reply reopens the ticket and puts it back in the queue." A reply is what reopens the ticket; an email without this line is a closed door with no handle.
In ticket.follow_up"If no response is received within the timeframe, this ticket may be automatically closed." The auto-close worker acts on this promise, so the promise stays.

Both are drawn on the canvas as required blocks and cannot be removed, reordered out of the body, or made conditional.

What gets sent a choice, not a layout

The owner asked to choose what information goes out. That is this panel, and it is kept out of the canvas on purpose: a paragraph is a way of saying something, and a switch is a decision about whether to say it at all. Every switch reads as a sentence with the consequence beside it.

Name the person it is addressed to Adds the greeting. When off, the message opens with the ticket line and the reader has to work out who they are from the address bar.
Show the ticket number and title On for all four customer-facing ticket messages today, because the number is the reference a client quotes back.
Quote what was said On for a note. Off for a status change, where there is nothing to quote — which is exactly the conditional drawn on the canvas.
Quote the whole thread, not just this note Off. Turning it on puts every previous note in the message; on a ticket with 12 comments that is a long email to somebody who asked one question.
Include time entries Off. Time logged is a customer-visible activity today and does notify the contact; making it a line in the message body as well would tell the client how long the work took on every update.
Include the status history Off. The current status is a fact pair; the history is a report, and a report belongs in a report.
Name the technician On. A named person is a person the client can ask for.
Show the client's own name in the footer On — and this is the paragraph the composer writes as a string literal today. Here it is a block with a switch behind it.

That is the whole reason the ladder is drawn as a ladder: on a message with an override at level 3, the person editing at level 2 needs to know their change will reach four clients and not one.

Why the way back is not optional

This is the first screen in the product that lets somebody change what a client reads without a deployment, a pull request or a code review. The default is preserved forever — the code keeps its own version, so reset to default is always available and always returns to a body that exists in the repository rather than to an earlier draft somebody has forgotten. Every save, restore, reset and test send is recorded with the person, the time and the difference, and the record names the version it replaced rather than only the version it created.

Screen five — What an internal message is not

The distinction the code already draws, and which messages are deliberately plain

One message of the ten goes to a member of staff. It is not the customer message with different words, it does not carry the brand kit, and it is not a place to be consistent with the others.

What the code says, in its own words two comments, quoted

"Internal, and therefore not the customer template with different words: it names who replied and quotes what they said, because the person reading it has to decide what to do about it and the client is already in the thread. The ticket's own page is the link — an internal email that asks somebody to reply by email would put the answer in the wrong place."

"An internal notification: a ticket the client has just reopened. Its own template rather than the customer one with different words. The reader is a technician who has to decide what to do next, so it names the person who replied and quotes what they said, and it links to the ticket instead of inviting a reply — the answer belongs in the thread, not in an inbox."

The section's job is not to repeat that. It is to make sure an editor cannot quietly undo it: the brand kit's logo, colours, marketing footer and unsubscribe line are not available on this message, and the section says why rather than presenting a lock with no reason.

What may change on this message
SenderToday it is SMTP_FROM, defaulting to noreply@cyber7group.com. The only address change allowed, and it matters more here than anywhere: a code from an address nobody recognises is a code somebody reports.
FooterPlain text, no logo, no marketing line, no unsubscribe — a transactional security message must not offer to unsubscribe from itself.
Brand kitNot available. Colours and type cannot be applied to this message, and the switch is drawn on and locked rather than hidden so the reason is visible: a brand kit is a design system for mail a client reads at leisure, and this is not that mail.
Attachments and inline imagesNot available. A message whose whole purpose is one short code should carry nothing that has to load, and every image is a load.
SubjectFixed. "C7NTAX — Your Verification Code" is what somebody looks for in a crowded inbox, and it is the phrase support tells them to search for.
The design decision, stated once and enforced everywhere Three of the ten messages are locked to a plain body. The section makes that a property of the message rather than a setting somebody can switch, it is visible on the list row, in the editor's class chip, on the locked block list and on the canvas plate — and it is the only place in the section where a control is drawn locked instead of absent.
In the classic interface

Administration → Email Studio, as four classic pages

One component, one set of handlers, two returns — the state, the API calls and the words are shared, the arrangement is not. In the classic interface the section is four pages under Administration, each built the way every other classic screen is built: labelled fields in a grid, a table where the modern screen has cards, and a dialog with a heading and Save/Cancel for anything that writes.

Page 1 — MessagesA table, not a rail of groups: Message, Key, Group, Trigger, To, State, Attachments as seven labelled columns, sorted and paged. "Which have we changed?" is answered by sorting on State, where the modern screen answers it with a badge you can see.
Page 2 — TemplateA form: Subject, From, Reply-to as text fields in a grid; the blocks as an ordered list with an Add block select and up/down/remove buttons; the selected block's properties in a labelled grid — Text, Font size, Colour, Align, Condition. Save and Cancel at the foot.
Page 3 — ContentThe switches as a fieldset of checkboxes with a label each, in the same order as the modern panel — the one part of the section that reads almost identically in both designs, because it is a list of choices and a list of choices is a form.
Page 4 — Preview & historyPreview is a Record <select> and a Preview button opening a dialog with the rendered message and a Width select (Desktop / Mobile) where the modern screen has pills and two frames side by side. History is a table whose Action column opens a restore confirmation dialog.

What differs on purpose, and what the Help walkthrough therefore has to say. The classic form keeps every field on screen at once; the modern editor reveals the selected block's inspector beside the block it belongs to, and hangs the conditional on the block as a rail rather than a value in a grid. The classic preview is one width at a time behind a select; the modern preview shows both widths at once, because the question being asked is "does it still read on a phone", and a select answers it one click at a time. The classic locked message is a disabled fieldset; the modern one is a plate on the canvas and a padlocked block list. The state, the calls and the sentences are the same in both.
