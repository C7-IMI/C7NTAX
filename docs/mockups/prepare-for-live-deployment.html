State one — the track

Eight steps, and the state of each one told the same way in every card

The plan's §6 order of work, with the plan's own exit conditions as the checks. A step is done, attention, blocked by a named thing, an owed decision, or could not verify. The last two exist because 2.3 is deferred by decision rather than forgotten, and because nothing in this package has touched ARM yet.

Done

The check ran and passed, with the evidence it was checked against.

Attention

Ran, and found something that needs a person — a placeholder, a known pre-existing failure.

Blocked

Cannot pass until a named thing changes. The card names the thing.

Decision owed

Not a task. An owner and a place to record the answer, not a checkbox.

Could not verify

The check did not run. Never shown as a pass — the round-2 defect was exactly this.

Advisories — they do not gate the deploy

State two — a step in detail

Step 5 · Readiness gate — six checks, each with its evidence and its cost of skipping

The step the second review was written about: a health gate that proved only that Node was listening, so a revision with a wrong DATABASE_URL, an unreachable server, a rotated password or a failed migration passed the probe and both gates and took 100% of traffic. Every item below says what it was checked against, and what happens if it is skipped.

Checklist — 6 items

4 done 1 attention 1 could not verify

A readiness endpoint exists, and it queries the database done

Checked against: apps/api/src/index.ts — GET /api/ready runs prisma.$queryRaw`SELECT 1` with a 2 s budget and answers { "status": "ready" | "not-ready" }, with nothing else in the body.

Skip it: the gate goes back to proving that Node is listening, and a revision that cannot reach c7ntax takes 100% of traffic.

Liveness stays shallow, on /api/health done

Checked against: the two probes are deliberately different — the readiness probe and both gates ask /api/ready; the liveness probe asks /api/health.

Skip it: a liveness check that queries the database restarts every replica in a loop and turns a database outage into a crash storm.

Both promotion gates ask it, not the script alone done

Checked against: scripts/azure/deploy-env.ps1 (the 0%-traffic gate) and .github/workflows/deploy-azure.yml — the path a production deploy actually takes.

Skip it: the pipeline promotes a revision the script's gate would have rejected, and the two promotion paths disagree about what healthy means.

The deep check is only on the gates, never on the first-run probe done

Checked against: ?deep=1 adds "the newest migration this image ships has been applied" and is passed by the two gates only.

Skip it: on a first run the app is created before the migration job, so a probe waiting on migration state holds the first revision at 0% — and the migration question is only answerable after migrations have run.

The unauthenticated endpoint leaks nothing attention

Checked against: the body says only { status: "ready" | "not-ready" } — no error, no host, no database name. Why attention: the same discipline has to hold for SKIP_PATHS in autoSnapshot.ts and the audit-log exclusions, which the endpoint was added to; a later route that echoes the failure would undo it.

Skip it: the host, the database name or a driver error is echoed to an unauthenticated caller — and the database name is not a secret, but a connection error is a map.

The runner's Azure CLI accepts the flags the update path passes could not verify

Checked against: nothing on this machine — no Azure CLI is installed here, so the claim that az containerapp job update accepts neither --mi-user-assigned nor --registry-identity is asserted from the CLI's own reference, not tested. The fix passes --image only.

Skip it: the first push takes the create branch and works; every push after it takes the update branch and fails at the migration step — the same outcome fix 1.8 produced, moved from the first push to the second.

What this step actually decides

Whether a revision earns traffic. Nothing here is a preference; it is the difference between a gate and a green light.

How it is run

pnpm deploy:dev # then: the 0%-traffic gate asks /api/ready?deep=1 curl -fsS https://<app>/api/ready # shallow, what the probe asks curl -fsS "https://<app>/api/ready?deep=1" # what the two gates ask

The distinction matters: the probe must stay shallow, and the gates must not.

State three — sanitisation

Strip the instance of what must not travel — and never confuse the two removals

Removing sample data is a reversible act with a snapshot behind it, run by a script. Removing a customer's real data is an irreversible act that belongs to the operator, out of band, with the customer's authorisation and a backup taken first. The two never share a button, and this screen performs only the first.

Remove sample and seed data

reversible

The real contract, from apps/api/src/sample-data-toggle.ts: snapshot first, then wipe the business models children-before-parents, then set the disabled flag — which locks the snapshot and stops automatic snapshot capture and auto-reseed. Identity and platform configuration are preserved, so the instance stays usable.

pnpm db:sample-off # npx tsx src/sample-data-toggle.ts off [SampleData] Capturing snapshot before clearing... [SampleData] Removing sample/business data... [SampleData] Removed N business records (identity & platform config preserved). [SampleData] Snapshot is locked — it will not be overwritten until sample data is re-enabled. [SampleData] Automatic reseed after changes is paused.
Reversible with pnpm db:sample-on

Remove a customer's real data

not done here

This is not a script in this wizard and not a button beside the one above. It is a destructive, irreversible act with a different owner, a different authority and a different recovery: written authorisation from the customer, a taken-and-restored backup, and an operator willing to sign for it. The wizard records the decision and refuses the act.

To proceed out of band, type the database name to confirm:
owner: the operator

What remains the operator's decision

None of these is a task. Each has an owner and a place to record the answer, because a checkbox that pretends a decision is done is worse than a blank.

D1 · Ingress: Front Door Premium alone, or Front Door and App Gateway

Recommendation: Premium alone, Blocking, with a Private Link origin — the reason is not only the ~$325/mo, it is that Premium is what makes the origin unreachable from the internet rather than merely restricted by a service tag.

2.3 · Password role now, or Entra passwordless now

Recommendation: app_c7ntax owning the public schema of c7ntax now, Entra as a follow-up — because before data exists this is a five-minute ownership change, and after it exists it is a migration with a credential rotation attached.

8.3 · Which secrets expire

Recommendation: expire the database credential (12 months); leave JWT_SECRET_VALUE and KUMO_MASTER_KEY_VALUE without expiry until rotation exists, tagged rotation=manual, reason=key-ring-not-implemented so the next reviewer sees a decision rather than an oversight.

8.5 · HA mode, and the reservation sized from it

A standby is billed in both HA modes, so the ~$130/mo choice is availability, not a saving: ZoneRedundant survives the loss of a zone, SameZone only a host failure, Disabled is the only ×1 mode. The reservation is sized ×2 for either mode.

What the classic arrangement keeps, and what it drops

Keeps: the numbered table of contents with a State column; a remarks field per unverifiable check, because a form has somewhere to write an exception; Save / Cancel on every step; and the sanitisation step as two separate panels with their own headings and their own Save — never one form with two buttons of the same colour.

Drops: the step track and its click-through, the destination pills (a select instead), the sticky countable footer (a labelled row of counts under the table), and the printed-report preview — the classic hand-off is a Print button and a summary grid, because the destination for a printed report is the same in both designs.
