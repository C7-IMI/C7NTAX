A “Why” control for each setting’s explanation

The settings tab is the tallest of the three because every field carries its reasoning with it: the one-line summary, then three or four lines of explanation, then what it changes and what it defaults to. Sixteen of those is a long page. The proposal here is to keep the label, the one-line summary and the control always visible — the three things you actually decide from — and fold the rest behind a small Why control beside the label, which opens the explanation in place.

Portal settings

Customer portal enabled

Deployment default (PORTAL_ENABLED)

Expose the portal and everything behind it.

When off, every portal route answers 404 and the sign-in page does not exist — a deployment that has not switched the portal on should not advertise it. Takes effect immediately; no restart.

Changes: /portal · Portal sign-in · Clients → Portal access

Default when nothing is saved: false

Portal address

Overrides PORTAL_PUBLIC_URL

The address a customer is given for the portal.

Leave this blank when customers reach the portal at this application's own address — the usual case, and the address is then worked out for you. Set it when the portal is served from somewhere else, such as https://portal.example.com or https://support.example.com/portal, and that becomes the address shown on the Portal card, copied for a welcome mail, and quoted in the sign-in email. Include the https:// and any path the portal sits under.

Changes: Portal card · Portal sign-in email

Default when nothing is saved: ""

Ticket visibility

Whether a customer sees only their own tickets or every ticket belonging to their client.

Contact (the default) shows a ticket the customer raised, is the contact on, or was added to. Client opens it up to everyone at the same client — right for a small business with one mailbox, wrong for a client with three hundred staff. Either answer can be changed for one client, or for one person, from Client access on the same screen.

Changes: Portal ticket list · Portal ticket detail · Portal ticket replies

Default when nothing is saved: "contact"

Sign-in code lifetime

How long an emailed sign-in code stays usable.

Long enough for a mail hop, short enough that a code read over someone's shoulder is useless later.

Per-client colours are set on the client record under Clients. Leave this blank to inherit the application's own theme.

The scaling is arithmetic on the height of the fields alone (the card's own heading and padding are the same in both designs), so treat the right-hand column as an estimate rather than a promise. The bar is drawn to the scaled figure.

What does not change

  • Every field, its label, its one-line summary, its control and where it saves from: untouched.
  • The chips that say where a value came from — “Deployment default (PORTAL_ENABLED)”, “Overrides …” — stay on the row, because they are what you notice without reading.
  • The explanation itself, the “Changes:” line and the default: all still there, one click away, and searchable with the browser's own find once opened.
  • Nothing is hidden from the API or from a screen reader: the Why control is a real button with aria-expanded, not a hover-only reveal.

Choices worth making

  • “Why” as a word rather than an ⓘ icon. An icon is quieter but says nothing until it is hovered; “Why” is self-explaining and reads as part of the label. The icon version is the fallback if the strip of chips and buttons gets busy.
  • One switch for the whole card (“Show every explanation”) so an administrator who is reading the screen like documentation can have today's behaviour back without opening sixteen fields.
  • The default and “Changes:” lines fold away with the explanation. They are reference, not decision — but if you would rather keep “Default when nothing is saved” visible, it is a one-line change in the same row.
  • Open state is per field, not remembered. A field opens because you asked; nothing is remembered between visits, so the page always comes back compact.
  • The same treatment fits the other long settings screens — Configuration and System Settings are built from the same field cards, so one change covers them.

Mockup only. No application file has been changed to produce this page: the markup borrows the app's classes and its compiled stylesheet so the comparison is honest, but the app still draws the “Today” layout — with its sixteen explanations — exactly as it does now.
