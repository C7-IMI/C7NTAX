The send sheet, and the way a document gets in

Six screens of one proposal: the moments a person actually sends something — a note to a client, an invoice, a report — and the mapping step that gets a Word, Publisher or PowerPoint document into the message safely. Every send is drawn in three states of confidence (before, during, after) with the recipient list it will use, every attachment is drawn with what it may carry and what it must never, and the importer admits in the interface what it cannot carry.

Screen one — the moment of sending

One sheet, three moments: a ticket note, an invoice, a report

The same panel opens from three places and is composed the same way every time: the recipient it will use, the template it will use (with a way to pick another), the subject, an editable body, the attachments it will carry, and a preview of the exact message. What changes is the contents — which is a separate list of switches, because the owner asked to choose what information gets sent, not how it is arranged.

Today. There are two ticket send paths, and they are not the same shape. A non-internal note calls notifyTicketContact and sends the ticket.activity template with the event label "New note added". The Reply dialog posts to POST /tickets/:id/email and sends the typed body wrapped by a string literal: <hr><p>Ticket: MSP-02-2013 — Office 365 license assignment<br>Client: Globex Industries</p>. There is no template to pick and no way to add the invoice PDF, the report PDF or a file from the ticket's own attachments. The invoice email has no such path at all: sendInvoice is written and unused, and the Send control is only drawn for a draft.
These are three entry points into one panel, not three panels: the state, the send call and the words are shared; the contents are not.

Screen three — what a message may carry

What it can attach, what it must never attach, and what happens when a file is too big

Carrying a PDF is a transport capability that already exists — send() takes attachments and cid inline parts. What does not exist is any surface that lets a person choose one. That surface has to answer three questions in the same place: where the file comes from, who is allowed to see it, and what happens when it will not fit through an SMTP server.

The real limits, read from the code. 5 MB per file (MAX_ATTACHMENT_BYTES in the editor's profile, and the error the user sees is "name is larger than 5 MB"); 10 files per send (req.body.attachments.slice(0, 10)); a 10 MB request body (express.json({ limit: "10mb" })); and for pictures pasted into the message, 2 MB each, 20 images, 8 MB in total, pulled out of the HTML into cid parts by extractInlineImages. There is no link-shortening, no signed-link service and no cloud storage in the send path: a file either travels in the message or does not travel.

Screen four — a document from outside

Drop a Word, Publisher or PowerPoint file in, and watch it turn into blocks

A Publisher newsletter is two columns, text boxes, a gradient band, an embedded font and vector art. None of that survives a mail client, and this application has to send mail that survives Outlook. So the import is not a conversion — it is a mapping and review step: what came across as a block, what came across as an image, and what will be dropped, with the choice offered per element, ending in a template that is visibly made of the same blocks the editor uses.

Today. There is no importer, and this screen is a proposal. Its only precedent is the paste path that already exists: cleanPastedHtml in RichTextEditor.tsx is explicitly "Word-aware paste", keeping italics, lists, tables, links and a fixed list of inline properties (PASTE_STYLE_PROPS: colour, background, font-family and size, weight, style, decoration, alignment, line-height, left margin and padding, vertical-align). Everything it lands must then survive emailHtml.ts, which is the real constraint: a known tag set, a much shorter style list, a drop-with-content list of script/style/iframe/object/embed/form/svg/template, unknown tags unwrapped with their text kept, and data-URI pictures pulled out into cid parts because Outlook renders none of them.

What it admits it cannot do
  • It cannot promise fidelity, and it does not try. What it promises is that you see the mapping before you send, element by element.
  • It cannot keep a two-column layout. Mail that reflows is mail that survives Outlook, so the columns become one — deliberately, in reading order.
  • It cannot keep a gradient, a texture, a shadow or an embedded font. The colour list and the font stack are finite, and Outlook's are smaller than a browser's.
  • It cannot keep vector art as art. The logo becomes a PNG, which means it is crisp at the width it was flattened at and soft at any other.
  • It cannot preserve pagination, page numbers or cross-references. An email is one reflowing column.
  • It cannot import a mail merge's data, or the field codes behind it — the fields become plain text until you point them at this product's own fields.
  • It cannot round-trip. Once it is blocks, it is not a Publisher file, and there is no export back.
  • It cannot recover what a mail client would strip anyway. Anything it kept that Outlook then removes would be a lie told twice, so it removes it here.

Seven template functions, and no way in

Every subject, every footer, every brand element and every paragraph of every message is a string literal in EmailService.ts or in the route that calls it. Changing a word in a client-facing email is a deployment. The catalogue above is why the sheet exists: the keys already have names, so the sheet has something to offer and the templates have somewhere to live.

The two dead ones are not a footnote

invoice.send is the owner's own request, already written. ticket.closure is the auto-close notice — note that the closure a person performs today does go out, as ticket.activity with the label "Ticket closed" and the sentence inviting a reply, through notifyTicketClosure; it is only the worker's version that nothing calls. Drawing either as existing behaviour would be the one thing this file must not do.

In the classic interface — the same send moment as a form

Classic: a labelled form in a grid, a dialog with a heading, a preview pane beside it

This repository keeps two designs of every screen and they are not one screen with a class toggled. The classic interface is a form: labelled fields in a grid, a modal dialog with a heading and Cancel / Send, a preview pane down the side that is visible rather than revealed, and a select where the modern screen has a pill you press. The words, the state, the contents list and the API call are shared. The arrangement is not — and what the modern sheet sheds that the classic dialog keeps is the flat list of every fact as a checkbox, in one column, in the order the fields appear.
