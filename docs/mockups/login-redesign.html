A sign-in page that answers one question

The current page asks who you are, then spends its remaining height on four health tiles, two identical passkey buttons and a toast that can expire before you finish reading it. This is the same page composed again: the way in is the first choice, the errors are at the field, the backend is one sentence when it is well and one sentence when it is not, and the four states that used to be four screens — credentials, second factor, a temporary password, a new passkey — are four steps in one card. Restraint is the whole design: nothing on the page moves, and nothing competes with the field you are typing in.

Today, from apps/web/src/pages/Login.tsx: a min-h-screen navy-950 surface, one 384px column — BrandMark 56, the C7NTAX wordmark, “Sign in to your PSA dashboard”, two fields that carry their names in placeholders (Email or username, Password — the password field has no autocomplete at all), one Sign In button, then Sign in with passkey and Register passkey on this device as two more full-width secondary buttons, then a caption over a 2×2 grid of four service tiles, the address this connection arrives from, and © 2026 Cyber 7 Group, LLC. Every error is a react-hot-toast toast. The second-factor step is a separate screen; MFA enrolment is /mfa-setup in the shell and is not part of signing in; an account on a temporary password signs in and is then swapped onto a full-screen gate on a different background that never says why.

Notes

The status, without tiles — and the two colours that were wrong

The status is the one part of this page that has to be believed, so it is the one part that was checked against the code that produces it rather than against how it looks.

Four tiles that are one probe, one of which never asked

  • “Web Server — Serving” is a tautology. The panel is the page; if the browser is rendering it, the frontend served it. The tile cannot be red.
  • The other three are a single request. All three derive from one fetch("/api/health"), so they are all green or all red — three blocks of colour where one fact would do, and no state in which two of them differ.
  • “Database — Connected” is not what the probe asked. In apps/api/src/index.ts, /api/health is deliberately liveness only — “is this process listening” — and must never query the database, or an outage becomes a crash storm. It answers {"status":"ok","version":"1.0.0"}. The honest probe already exists at /api/ready, answers {"status":"ready"}, and is unauthenticated, so this page can ask it. The redesign does.
  • The remedy is written for the wrong reader. When the API is down, three tiles tell a person signing in to run pnpm dev in apps/api and to check port 4000 with netstat. That text is kept — it is accurate and it is somebody's morning — but it moves into the disclosure, under “For whoever runs this instance”, where the person who can use it will find it and the person signing in does not have to read it.

What the eye is given, and where trust comes from

  • One path. Mark → one sentence → the choice → the field → the act. Nothing else is at display size, and nothing on the page is a decoration that could be mistaken for a control.
  • Trust is not a badge. It comes from the mark and the product name being the real ones and undecorated, from messages in the product's own voice with no error codes, and from two facts that can actually be checked: the address this connection arrives from (GET /api/auth/client-ip) and the raw probe answers, each one press away.
  • Honesty is a feature of the state. When the API cannot answer, the page says sign-in cannot complete before a password is typed — and switches the act off rather than leaving it to fail, because a live button under that sentence is the page arguing with itself. The “Connecting from” line is absent in that state because the address cannot be read — which is the fastest way to see the API is down, and is kept.
  • Nothing is carried by colour alone. Every service states its own word — Serving, Healthy, Connected, Available, Unreachable — and the dot only repeats it.

The app's --btn-primary-fg exists for exactly this and is defined only inside the eight colour schemes at the end of index.css, every one of which fills with a dark red and therefore needs a white label. The default theme's cyan accent needs the opposite ink and never gets it, so Sign In — the only control on the page that matters — is white on cyan today. The same fallback reaches the redesign's own .tab-active.

Keyboard, screen reader, narrow window

  • Real labels. <label for>, not placeholders. The password field gets autocomplete="current-password" — today it has none, so a password manager can fill the first field and not the second.
  • A real radiogroup for Passkey | Password, so arrow keys move between them and a screen reader announces the choice and its effect; two aria-pressed divs would announce neither.
  • Errors are announced where they are read. role="alert", aria-invalid, aria-describedby pointing at the message, focus moved to the field. The notice is role="status" (polite) and the system line is aria-live="polite", so a service going down is announced without stealing focus mid-typing.
  • Tab order is the visual order — method, account, password, act, then the disclosure and the two footnotes. The reveal control is a 36px button named “Show password”.
  • 380px and 100% zoom: the mark drops to 40px, the card keeps 16px gutters, the segmented control stays on one line, and the status sentence wraps to two rather than clipping. At 100% zoom on a 640px-tall window, mark + sentence + choice + two fields + act + status fit above the fold without scrolling.
  • Nothing animates except a 150ms colour transition and the disclosure chevron — and the spinner on a busy button, which is suppressed under prefers-reduced-motion.

Deliberately absent

  • “Forgot password?” — there is no self-service reset in this product: no route in App.tsx, no handler in auth.ts. A link to an absent flow is worse than the sentence that names the only remedy that exists (“ask an administrator”), so the locked state names it and nothing is drawn that cannot happen.
  • “Remember this device” / “Keep me signed in” — the session model is the cookie and its configured timeout. Inventing a control here would promise something the API does not do.
  • Any SSO button on this instance — GET /api/auth/sso/status answers {"enabled":false} on 9 October 2026, so there is none; the state where an administrator has switched it on is drawn in the storyboard.
  • A passkey button on a browser without WebAuthn — Login.tsx already gates on PublicKeyCredential; the redesign keeps that and removes the segmented control entirely rather than showing an option that will fail.
