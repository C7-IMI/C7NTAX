What every message inherits, where it is sent from, when it may go, who may receive it — and what happened to the last few

The editor — the message list, the blocks, the preview — is drawn in email-studio.html, and the send sheet and the importer in email-send-and-import.html. Neither can answer the questions this file answers: a template is useless if nobody knows what it inherits, which address it leaves from, whether it is allowed to send at 2 a.m., who is suppressed, and which wording actually went out on Tuesday. Seven screens, one file.

What exists today, read from the repository and the running instance: the entire email system is one file — packages/email/src/EmailService.ts — with seven template functions, every one a string literal, beside a comment that reads "inline HTML, production should use MJML". There is no template store, no brand store and no record of any send. A single defaultFrom taken from SMTP_FROM (C7NTAX <noreply@cyber7group.com> on this instance) is used for every message, and send() takes no reply-to at all. Eight messages are live; two senders are written and never called; four more are proposed. The instance's relay is localhost:587 with no credentials — which the screen below treats as the honest case it is.

The unsubscribe rule: it goes on the messages a person may refuse, and on no others

There is no marketing in this product, so "unsubscribe" cannot mean what it means in a newsletter. It applies to exactly two things — report.scheduled sent to a client, and the activity digest when it is the only thing that can be stopped — and it links to the client's suppression page rather than a third-party list. An invoice notice, a closure email, a portal sign-in code and an MFA code carry no unsubscribe link: they are the delivery of a service the recipient asked for, and a link offering to stop them would be a lie.

Why a ticket notification replies into the ticket

Because that is how a reply gets back into the queue. A reply to a customer notification carries the subject tag the product put there — [INT-01-2006] — and the inbound connector matches it (TICKET_TAG_PATTERN in packages/email/src/EmailConnector.ts, which understands this product's own ticket numbers, not just a generic pattern) and appends it to the ticket. A reply addressed to a person lands in that person's inbox and stops being a ticket.

Today no Reply-To is set at all; the reply returns to whatever SMTP_FROM names, and threading relies entirely on the subject tag surviving
Proposed Reply-To is the connector's mailbox, so the answer arrives where the connector is watching rather than at noreply@
A code gets no reply-to, ever

The section refuses to hold one for auth.mfa_code, auth.password_changed, user.password_reset, portal.login_code or user.invite. A reply to a one-time code must not become somebody's support mail.

Domains — and the three things a person must not get wrong

Sending domain cyber7group.com — read from the configured SMTP_FROM
Return-path the relay's own; set by the relay, not by this application
Cloud delivery EMAIL_GRAPH_ENABLED — on by default; off, outbound mail uses the SMTP relay
SPF

One SPF record, and it must name every sender. A second v=spf1 TXT on the same name is a permanent error, not a merge — the receiver fails the whole check. Adding the relay's include is an edit to the existing record, not a new one.

DKIM

The selector is part of the key's name. Publish the public key at <selector>._domainkey.<domain> and give the same selector to whoever signs — get them out of step and every message fails DKIM while looking correctly configured.

DMARC

Alignment, not just passing. A message can pass SPF on the relay's domain and still fail DMARC because the From header is this domain. Start at p=none with a reporting address, watch it, then move to quarantine — never jump to p=reject on a domain that also sends real mail.

Records — the application reads what you paste, and says what it cannot see

Proposed. The section cannot reach your DNS provider and does not pretend to: it holds the records you paste and checks the two things a string can be checked for — that the value has the shape the standard requires, and that it names the relay this instance actually sends through.

TXT @   v=spf1 include:<your relay's include> -all
TXT c7ntax._domainkey   v=DKIM1; k=rsa; p=<public key from the relay>
TXT _dmarc   v=DMARC1; p=none; rua=mailto:dmarc@cyber7group.com

Illustrative shapes only — the include, the selector and the key are yours to paste. The application's job is to notice when the value it is given is not one of those shapes, or names a different relay from the one in SMTP_HOST.

What the application cannot verify — stated on the screen, not in a footnote

It cannot send mail from a domain it has not been allowed to: the From must be an address the relay accepts, and nothing here can grant that permission. It cannot prove a record you have not pasted. It has no view of your DNS provider, no live DMARC report feed, and no way to tell a misconfigured record from an unpublished one — so a paste is recorded and checked against the shape, and the section says "pasted, not confirmed" rather than "verified".

What it can do — and already does

Report the relay it was started with, field by field: configured · host · port · secure · hasCredentials · from from GET /api/system/deployment, guarded by Permission.SystemConfig — plus verify() on the transporter, which answers only whether the relay answered.

Screen four — Quiet hours, batching and the digest

Six changes in an hour are one digest, not six emails — and four messages never wait at all

A ticket that is updated, reassigned, re-prioritised, annotated, escalated and then closed inside an hour is ordinary. Whether the client receives six emails about it is a policy, and the policy should be the same for every client unless one client asks to differ.

The rule, as a track — one ticket, one hour, six events

Ticket NOC-05-2007 ("CPU sustained at 100% on app node", Stark Enterprises) is the shape this is for. Six customer-visible changes inside the hour, three messages instead of six.

First event

A status change. It is customer-visible, so a window opens and a count starts.

t + 0:00 · 1 of 3
Second event

A note is added. It joins the open window rather than starting its own email.

t + 0:06 · 2 of 3
Threshold reached

The third event trips the threshold: the window is now a digest, and the clock resets inside it so a long thread cannot push the send out all evening.

t + 0:17 · digest armed
Digest sends

One email listing every event in order with its own timestamp, in the words the single-event email would have used, one after another.

t + 0:32
Sixth event

After the digest, a new window. If it is the only event it goes as itself — a lone change does not wait 15 minutes to be told about alone.

t + 0:51 · 1 of 3
A lone event sends immediately

The window is not a delay applied to everything — it is a hold that only becomes real if a second event arrives inside it. One change is sent at once. That is why the ceiling matters more than the window: the ceiling is what stops a busy ticket being silent for an afternoon.

What is deliberately not batched or held

The exemptions are not preferences — each one is a message whose value is destroyed by waiting. Drawn as locked rows in the matrix too, so the rule is in two places rather than one paragraph.

auth.mfa_code — never held, never batched

Expires in 10 minutes and is read once, in a hurry, on the worst connection of the day. A digest of two of them is not a thing that can exist.

portal.login_code — never held, never batched

Same reason, and the rate limit is already there (codesPerWindow 3 per codeWindowMinutes 15): holding a code back would make the client wait on the product's convenience.

ticket.closure — never held until morning

A closure carries an instruction: "reply to this email — the reply reopens the ticket". Sent at 21:40 it is still read at 21:45 by someone who was waiting for it. Held to 07:00 it would tell them a ticket was closed eight hours after they saw it close.

ticket.reopened_internal — never batched

Internal, and the whole point is that a reopened ticket with no reader is the failure it exists to prevent.

Opt-out — proposed, and deliberately narrow

What it suppresses report.scheduled sent to a client, and the activity digest when it is the only remaining thing to stop
What it cannot suppress a closure, a follow-up, an invoice notice, a portal code, an MFA code — these are service delivery, and the section says so on the screen rather than letting somebody discover it

An opt-out that only removes a link from a footer is not a rule; the drop has to happen where the message is addressed.

Bounce and complaint — proposed, and a rule the application enforces

SignalWhat happens
Soft bounce
4xx, mailbox full		 Three attempts, then logged as failed. Not suppressed — a full mailbox is a Tuesday.
Hard bounce
5xx, no such user		 Counted. Two consecutive hard bounces suppress the address and it is dropped from every future recipient list — the same drop as an opt-out, so one place enforces both.
Complaint
an ARF report, or Graph's reported-spam		 Suppressed immediately, on one signal. Someone marking a message as spam is a fact about the message, not about their mailbox.
Both suppressions are visible on the recipient screen and reversible by a named person — a suppression nobody can lift becomes a client nobody can email, discovered six months later.
Applied in the sender for the drop, and the delivery log for the record — the bounce is only useful if it is attached to the message that caused it

Today there is no bounce handling of any kind: the addresses in this instance end in @example.com and @acmecorp.com, the relay is localhost, and a send that fails is only a logger.warn line — "Delivery is best-effort — failures are logged and never thrown, so callers are never blocked or broken by SMTP." That sentence is the reason this panel is a proposal rather than a description.

The four lines behind anything that did not go

A bounce code on its own is not an explanation, and "failed" on its own is not a fact a person can act on. Every non-delivery carries the same four lines, in the same order, whether the cause is a suppression, a relay refusal or a missing sender.

What happenedthe mechanism, not the symptom — 550 5.1.1, "skipped: address suppressed", "no sender wired"
Whythe rule or the cause — bounce 1 of 2, opt-out set on this date, exemption not applicable
What to dothe next action, and whether Resend is capable of it
Evidencethe record the screen is reading, so the four lines can be checked

Resend — and the one thing it must not pretend

What Resend does re-renders the message as it was — the version recorded on the row, not the current template — and sends it again to the same recipient, recording a second row rather than overwriting the first
What it refuses a suppressed address, and a row whose failure was "no sender wired". A button that says Resend and cannot resend is worse than a disabled one.
Template version proposed: the template's own revision, stamped on the row at send. Today there is no such thing — the wording is a string literal in EmailService.ts, so the only honest version is the build's. The column exists so that when the editor lands, "which wording went out on Tuesday" already has an answer.
Where it is applied the sender re-renders and re-sends; the API owns the row and the reason. Neither is in the interface, so a resend is the same act whether it came from this screen or from a retry.

What differs on purpose, and what the Help walkthrough therefore has to say. The classic matrix keeps all six columns visible as a sortable table and disables the checkbox rather than colouring the row; the modern one filters by group and marks the locked rows with a lock chip. The classic brand kit shows the values as form fields in a grid; the modern one shows the kit applied to a real message in the same screen, because "the footer looks like this" is easier to check than to imagine.
