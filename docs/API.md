# The C7NTAX API

**Audience:** whoever is connecting something to C7NTAX — an RMM, an SIEM, a monitoring platform, an
accounting system, a scheduler, or a script somebody wrote on a Friday.

This document explains how to authenticate, how to send and read things, and — for the four kinds of
integration the application was built to accept — the recipe to follow. The exhaustive, per-endpoint
reference is [`openapi.yaml`](./openapi.yaml), which is **generated from the routes the API declares**
and therefore cannot describe an endpoint that does not exist. When this guide and the specification
disagree about a field name, the specification is right and this file is a bug.
Interoperability with the companion RMM app has its own (draft, planning-stage) document:
[`INTEGRATION-CONTRACT.md`](./INTEGRATION-CONTRACT.md).

---

## 1. Where the API is

| | |
|---|---|
| Base path | `/api` — e.g. `https://psa.example.com/api` |
| Local development | `http://localhost:4000/api` (the web app runs separately on `http://localhost:3010`) |
| Format | JSON in, JSON out (`content-type: application/json`) |
| Health | `GET /api/health` — the only route that needs no credential |
| Specification | [`docs/openapi.yaml`](./openapi.yaml) — OpenAPI 3.1, one path per route |

The document is generated by [`scripts/generate-openapi.mjs`](../scripts/generate-openapi.mjs) from
`apps/api/src/routes/**`, the mount points in `apps/api/src/index.ts` and the permission enum in
`packages/shared/src/enums.ts`. Anything a parser can derive is derived; the prose that a parser
cannot invent lives in [`docs/api-operations.json`](./api-operations.json), keyed by `METHOD /path`.
See §13 for what to do when you change a route.

## 2. Two credentials

Both are sent in the same header, so a client does not need to know which kind it holds:

```
Authorization: Bearer <session token or API key>
```

| | Session token | API key |
|---|---|---|
| Issued by | `POST /api/auth/login` | `POST /api/api-keys` |
| Looks like | an opaque JWT-ish string | `c7k_<16 hex characters>.<secret>` |
| Belongs to | the person who signed in | an account, named on the key |
| Power | everything that account may do | **the key's scopes ∩ the account's current permissions** |
| Lifetime | short, refreshed or extended | as long as it is not revoked, and optionally until `expiresAt` |
| Good for | a person, a browser, an interactive script | a server, a device, a scheduled job |

### 2.1 Signing in

```bash
curl -s https://psa.example.com/api/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"api@yourmsp.com","password":"…"}'
```

```json
{
  "token": "…",
  "user": { "id": "…", "email": "…", "role": { "…": "…" } },
  "landingPage": "/",
  "mustChangePassword": false
}
```

A response with `"mfaRequired": true` means no token was issued: send the returned `mfaToken` and the
six-digit code to `POST /api/auth/mfa/verify` (e-mail codes use `POST /api/auth/mfa/verify-email`).
`POST /api/auth/me` describes the caller, `POST /api/auth/session/extend` pushes the expiry out, and
`POST /api/auth/logout` ends it. A session token is tied to the account's password and session
version: changing the password invalidates tokens issued before it.

Signing in is rate limited hard (see §5), and a wrong password repeatedly will lock the account. For
anything unattended, use an API key.

### 2.2 API keys — the credential for a program

An API key is a credential that acts **as an account**, narrowed to a set of permissions. Issuing one
is the same kind of act as creating a user, so it is gated on `user:manage`, and every issuance,
rotation and revocation is written to the audit log (`entity: "api_key"`).

```bash
# 1. What can a key be given? (permissions and source kinds)
curl -s https://psa.example.com/api/api-keys/permissions -H "authorization: Bearer $ADMIN_TOKEN"

# 2. Issue one, for an RMM that may only raise and view tickets
curl -s -X POST https://psa.example.com/api/api-keys \
  -H "authorization: Bearer $ADMIN_TOKEN" -H 'content-type: application/json' \
  -d '{
        "name": "RMM — Acme tenant",
        "sourceKind": "rmm",
        "description": "Raises alerts from the RMM poller",
        "permissions": ["ticket:create", "ticket:view"],
        "expiresAt": "2027-01-01T00:00:00.000Z"
      }'
```

The response contains the secret **once**:

```json
{
  "id": "…", "name": "RMM — Acme tenant", "prefix": "c7k_1f4c9ab73e2d5061",
  "key": "c7k_1f4c9ab73e2d5061.<43 characters>",
  "permissions": ["ticket:create", "ticket:view"],
  "sourceKind": "rmm", "state": "active",
  "warning": "This is the only time the key is shown. …"
}
```

* **Only a hash is stored.** The list (`GET /api/api-keys`) returns the prefix and the metadata, never
  the secret. A lost key is rotated (`POST /api/api-keys/{id}/rotate`), not recovered — which is what
  makes rotation mean something.
* **Scopes are an intersection, not a grant.** The key may never do more than the account it belongs
  to, and the account's permissions are re-read on every request, so removing a permission from the
  account removes it from every key that account owns — immediately, without touching the key.
* **Scopes are validated at issuance** against the permissions the application actually has, so a key
  asking for a permission nobody holds is refused rather than silently useless.
* **States.** A revoked key, an expired key, and a key whose account has been deactivated are all
  `401`, with the same shape as a bad password. Deletion is revocation: the row is kept, because the
  inventory is a credential history.
* **`sourceKind`** is free labelling from the list
  `["rmm","siem","flexpoint","quickbooks","monitoring","scheduler","other"]`. It shows up in the UI
  and in the key's `AuditLog` rows; it does not restrict anything.
* Keys are issued and managed on **Administration → API access** in the application, or through the
  same endpoints (`GET /api/api-keys?includeRevoked=true` for the full history).

## 3. Making a request

```bash
curl -s https://psa.example.com/api/tickets?status=open&limit=10 \
  -H "authorization: Bearer $C7_KEY"
```

Conventions worth internalising:

* Collections answer with a `data` array; single records answer with the record itself.
* Entity ids are opaque strings (cuid). Do not parse them.
* Unknown fields are ignored rather than rejected, so adding a field to your sender does not break
  when the receiving end is an older version.
* String comparisons on names are case-insensitive where they are used for lookup, and a lookup that
  would match more than one record is refused rather than guessed (see §7).

## 4. Errors

The error handler answers with an object:

```json
{ "error": { "message": "title and boardId required", "status": 400 } }
```

with `details` added when the failure has more than one part (validation lists, for instance). A few
handlers — the rate limiter among them — answer with a plain string instead, so a client should read
`error.message` when it is an object and `error` when it is a string.

| Status | Meaning |
|---|---|
| `400` | Understood and refused: a missing field, a contradiction, a name that matches nothing |
| `401` | No usable credential — missing, malformed, expired, revoked, or the account is deactivated |
| `403` | Authenticated, but the credential does not hold the permission the operation needs |
| `404` | The record is not there, or is not visible to this credential |
| `409` | A conflict: a duplicate, or a lookup that matched more than one record |
| `423` | The account is locked after too many failed sign-in attempts |
| `429` | Rate limited — see §5 |
| `500` | An unhandled failure. The message is deliberately generic; the detail is in the API log |

A `403` and a `404` are sometimes the same thing from the outside, on purpose: a client-scoped account
asking for another client's ticket is told it is not there, not that it exists and is forbidden.

## 5. Rate limits

* **Global:** every `/api` request is counted per client IP — currently **9,999 requests per minute**,
  which is a backstop against a runaway loop rather than a subscription tier.
* **Credentials:** `/api/auth/login` and the MFA routes have a much tighter limiter, because they are
  the endpoints worth guessing at.
* **Every response carries** `X-RateLimit-Limit`, `X-RateLimit-Remaining` and
  `X-RateLimit-Reset` (seconds since the epoch).
* **A refusal is** `429` with `{ "error": "Too many requests", "retryAfter": <seconds> }`.

Counters live in the process's memory. Behind more than one instance the effective limit is per
instance, and a restart clears them — a client should still honour `retryAfter` rather than assume a
window.

## 6. Listing, filtering, paging

Most collections take `limit` and `offset` and answer with the page and the total:

```bash
curl -s "https://psa.example.com/api/clients?limit=25&offset=50&sort=name&status=active" \
  -H "authorization: Bearer $C7_KEY"
```

```json
{ "data": [ … ], "total": 137, "limit": 25, "offset": 50 }
```

* Defaults are `limit=50`, `offset=0`; `GET /api/events` caps `limit` at 200.
* `search` is a case-insensitive contains across the fields that matter for that entity.
* Multi-value filters accept a comma-separated list: `GET /api/tickets?status=waiting_on_client,waiting_on_third_party`.
  `status=open` is shorthand for everything not closed or cancelled.
* `sort` accepts only the fields that collection allows; anything else falls back to the default
  rather than erroring.
* Page by offset for reports and by `createdAt` ordering for syncs, and be aware that a large offset
  is a scan: for bulk reads, prefer a narrower filter.

## 7. The event gateway — RMM, SIEM, monitoring

This is the path to use when another system needs to *tell* C7NTAX that something happened. One
endpoint serves every vendor, because an alert from an RMM and a detection from an SIEM are the same
shape of message:

```
POST /api/events        permission: ticket:create
GET  /api/events        permission: ticket:view      what has arrived, with the ticket it became
GET  /api/events/sources permission: ticket:view     which systems have sent, and how much
```

**The design decision you have to co-operate with is `(source, externalId)`.** A monitoring platform
that polls every minute will see the same failing service sixty times an hour. If each poll opened a
ticket, the queue would be useless, so:

* the first event with a given `source` + `externalId` **opens one ticket**;
* every repeat **attaches to that ticket** as an internal comment carrying an occurrence count, and
  answers `200` with `"merged": true`;
* `kind: "recovery"` **closes** the ticket the alert opened — it does not open anything;
* the payload is kept, on the event row and in the ticket's `customFields.event` / `customFields.data`,
  because the reason a ticket exists is usually in the part of the JSON nobody mapped.

### Request

| Field | Required | Notes |
|---|---|---|
| `source` | yes | Who is sending. `"rmm"`, `"siem"`, `"monitoring"`, `"sentinelone"`, `"splunk"` — any name. Sets a `source:<name>` tag on the ticket. |
| `externalId` | yes | **Your** id for this condition, stable across repeats. An alert id, a detection id, a check id. |
| `title` | yes | The ticket title. |
| `kind` | no (default `alert`) | `"recovery"` closes; anything else opens or joins. |
| `severity` | no (default `info`) | `critical`\|`high`\|`medium`\|`low`\|`info` → ticket priority `critical`\|`high`\|`medium`\|`low`\|`low`. |
| `description` | no | Markdown-ish text; lands in the ticket description and the first comment. |
| `client.companyId` | see below | The client the ticket belongs to. |
| `client.name` | see below | Used only when exactly one client carries that name. |
| `boardId` | no | Which board. Defaults to the intake board, then the oldest board. |
| `ticketId` | no | Append to this ticket instead of letting `externalId` decide. |
| `occurredAt` | no | ISO date — when it happened, as opposed to when you told us. |
| `data` | no | Anything. Kept verbatim. |

A ticket has to belong to somebody, so an event that names no client and matches none is **refused**
(`400`) rather than filed against a guess. The board is resolved in this order: `boardId` →
the configured intake board → the first board created; if there are no boards at all, the event is
refused with an explanation.

### Answers

| Case | Status | Body (abridged) |
|---|---|---|
| New event, ticket opened | `201` | `{ eventId, ticketId, ticketNumber, created: true, merged: false, recovered: false, occurrences: 1 }` |
| Repeat of a known event | `200` | `{ …, created: false, merged: true, occurrences: n }` — a comment was added |
| Sent to an explicit `ticketId` | `201`/`200` | `{ …, created: false, merged: true }` |
| Recovery with no ticket to close | `202` | `{ eventId, created: false, recovered: true, note: "No open ticket was tied to this event…" }` |

`occurrences` is the running count for that `(source, externalId)`, so a sender can log how much of a
flap it caused.

### Recipes

**An RMM alert, from a poller:**

```bash
curl -s -X POST https://psa.example.com/api/events \
  -H "authorization: Bearer $RMM_KEY" -H 'content-type: application/json' \
  -d '{
        "source": "rmm",
        "externalId": "alert-88213",
        "kind": "alert",
        "severity": "high",
        "title": "Disk space below 5% on DC01",
        "description": "C: has 3.1 GB free.",
        "client": { "companyId": "cm3xk…" },
        "occurredAt": "2026-10-08T02:11:04Z",
        "data": { "device": "DC01", "check": "disk.c", "freeGb": 3.1, "policy": "Servers / Disk" }
      }'
```

**…and the recovery, when the check passes again.** Same `externalId`, and the ticket closes:

```bash
curl -s -X POST https://psa.example.com/api/events \
  -H "authorization: Bearer $RMM_KEY" -H 'content-type: application/json' \
  -d '{ "source": "rmm", "externalId": "alert-88213", "kind": "recovery",
        "title": "Disk space back above 5% on DC01" }'
```

**A SIEM detection** is the same call with a different `source`, and the detection id as the
`externalId`:

```bash
curl -s -X POST https://psa.example.com/api/events \
  -H "authorization: Bearer $SIEM_KEY" -H 'content-type: application/json' \
  -d '{
        "source": "sentinelone",
        "externalId": "threat-5f21c9",
        "severity": "critical",
        "title": "Ransomware behaviour blocked on WKS-042",
        "client": { "name": "Acme Manufacturing" },
        "data": { "threatName": "…", "agentVersion": "…", "mitigation": "blocked" }
      }'
```

**Choosing `externalId` well** is most of the integration. It should identify the *condition*, not the
observation: an alert id, a resource id plus a check name, a detection id. If your platform's id
changes on every poll, use something stable instead (`"{deviceId}:{checkName}"`) — otherwise you will
get one ticket per poll and you will be right to blame the integration.

**Flap control.** A condition that clears and returns is a new event if you close and re-open with a
new id; with a stable id, the same ticket collects both. If you want a fresh ticket after a genuine
resolution, send the recovery, then a *new* `externalId` (for example append the re-open timestamp) for
the next occurrence.

**Inspect what you sent:** `GET /api/events?source=rmm&limit=20` returns the event rows with the ticket
each became, and `GET /api/events/sources` gives per-source totals and the last time each was heard
from — the fastest way to answer "is our SIEM key still working?".

**Where alerts land.** The intake board is on **Administration → API access**, and is also one call:

```bash
curl -s -X PATCH https://psa.example.com/api/system/config/eventIntakeBoardId \
  -H "authorization: Bearer $ADMIN_TOKEN" -H 'content-type: application/json' \
  -d '{ "value": "cm3board…" }'
```

(`system:config` required for both.) Without it, the oldest board is used.

## 8. Writing to the PSA directly

Events are the right shape for *incidents*. For anything else — a project sync, a scheduled import, a
script that creates a ticket from a form — write to the domain endpoints. Two things to know before
you do:

* **Comments e-mail the customer; internal ones do not.** `POST /api/tickets/{id}/comments` (body in
  `body`), `POST /api/tickets/{id}/notes` (body in `content`), and `PATCH /api/tickets/{id}` with a
  `note` all notify the ticket's customer contact unless `isInternal: true` (for `PATCH`, the flag is
  `noteInternal`). An integration that writes status updates should be explicit about this rather
  than surprised by it. Status changes notify too, when the status is one the customer is told about.
* **Ticket creation needs `title` and `boardId`**; `companyId`, `priority`, `source`, `contactId`,
  `assignedToId` and `additionalContactIds` are optional, and `POST /api/tickets/:id/time` adds the
  time entry that a status change alone does not.

Everything available is in the specification. The five endpoints that cover most integration work:

| Purpose | Endpoint | Permission |
|---|---|---|
| Create a ticket | `POST /api/tickets` | `ticket:create` |
| Update status / priority / assignee | `PATCH /api/tickets/{id}` | `ticket:edit` |
| Add a customer-visible or internal note | `POST /api/tickets/{id}/comments` | `ticket:edit` |
| Log time | `POST /api/tickets/{id}/time` | `ticket:edit` |
| Resolve the client a name refers to | `GET /api/clients?search=…` | `client:view` |

## 9. Connectors — reading from, and pushing to, other systems

Connectors are configured in **CloudConnect** and stored as `Integration` rows with encrypted
credentials. They read on a schedule and write only where a write has been configured, deliberately:
the PSA does not own the reference data an accounting system needs.

```bash
GET  /api/cloudconnect/types            # what can be connected, and which credentials each needs
GET  /api/cloudconnect                  # the connections, with their status
POST /api/cloudconnect                  # create one
POST /api/cloudconnect/{id}/test        # prove the credentials before trusting them
POST /api/cloudconnect/{id}/sync        # sync now, rather than waiting for the timer
GET  /api/cloudconnect/{id}/sync-logs   # what each sync did
GET  /api/cloudconnect/{id}/synced-entities
```

### Reporting on what a connector brought in

Connector data is reportable, not just visible. The read endpoints under `/api/reports/data/…`
answer the same `from`, `to`, `clientId` and `boardId` filters and add their own where the question
has them:

```bash
GET /api/reports/data/m365-inactive-accounts
    ?inactiveDays=90&includeDisabled=true&includeUnknown=true&tenantId={integrationId}&clientId={companyId}
# → accounts, byClient, byTenant, coverage, totals, notes
```

`inactiveDays` is the threshold (1–730, default 90); `includeDisabled` and `includeUnknown` decide
whether accounts already switched off, and accounts with no sign-in activity recorded, are listed —
an unknown sign-in is **never** counted as dormant, and the payload's `notes` says when sign-in
activity could not be read at all. Requires `report:view` **and** `integration:view`, because it
names individual accounts across tenants. The same endpoint backs the **Inactive Microsoft 365
Accounts** standard report, so the screen, the print-out and the CSV are one implementation.

### Microsoft 365 account hygiene

The Microsoft 365 sync brings in each tenant's users with their sign-in activity where Azure will
report it. That data has two uses and they live in different places on purpose: the **accounts of one
tenant** are shown with the tenant, on its connection under CloudConnect → Configuration (with the
offboarding action beside them), and the **question across every client and tenant** is the standard
report above, where it can be filtered to one client, printed and exported.

### FlexPoint (accounting)

FlexPoint is integrated natively rather than as a generic push, because its API is stable enough to
read and write against. The configuration screen is **C7NC → FlexPoint**; the whole surface is also
available to an integration:

```bash
GET  /api/flexpoint                     # connection, options, last sync, counts
PUT  /api/flexpoint/options             # which sync directions and writes are enabled
POST /api/flexpoint/sync                # pull customers, invoices, deposits
POST /api/flexpoint/link                # match FlexPoint customers to clients
GET  /api/flexpoint/clients/{companyId} # one client's receivables, as FlexPoint has them
GET  /api/flexpoint/invoices            # invoices, with their FlexPoint state
POST /api/flexpoint/invoices/{invoiceId}/push   # create or update the invoice in FlexPoint
```

Writes are **off by default** and enabled per option. When a push happens, the FlexPoint id is stored
on the invoice (`flexpointInvoiceId`, `flexpointPushedAt`) so a second push updates rather than
duplicates. Settled deposits come back as `Payment` rows (method `flexpoint`, reference
`flexpoint:<id>`), which is what makes the client's receivables view agree with the accounting system.

### QuickBooks Online, and any other accounting push

QuickBooks connects with `clientId`, `clientSecret`, `realmId` and `accessToken`
(`GET /api/cloudconnect/types` returns this list per provider). Because every provider wants different
reference data, records are pushed to a **URL you configure** on the integration
(`settings.expensePushUrl`, `settings.invoicePushUrl`) with the integration's own auth headers, and the
outcome is recorded on the record. A push that cannot happen says why — a missing URL, a refused URL,
an HTTP error — instead of pretending the record arrived.

Outbound requests from connectors and pushes go through the egress policy
(`apps/api/src/services/egress.ts`), which refuses private-network and non-HTTPS destinations.

### Microsoft 365: deploying the app registration

The email connector reads a Microsoft 365 mailbox with an **app-only** `Mail.ReadWrite` registration, so
something has to exist in the tenant before the connector can be saved. `O365/New-C7NTAXMailboxApp.ps1`
does it from a terminal; the same sequence is available as an API so a wizard can drive it inside the
product (Administration → CloudConnect → Email Connectors → **Deploy OAuth app**):

```bash
GET  /api/oauth-app                    # the permissions, the redirect URI, the by-hand command
POST /api/oauth-app/start              # a device code for the tenant administrator
POST /api/oauth-app/{id}/poll          # pending → authorized | declined | expired
POST /api/oauth-app/{id}/deploy        # create or reuse, consent, mint the secret
POST /api/oauth-app/import             # or read the script's out/c7ntax-m365-app.json
```

Sign-in is the OAuth **device-code** flow against Microsoft's public Graph command-line client, so this
application never holds a credential for the tenant: the administrator approves a code in their own
browser and the token that comes back is used for one task. Deployment is idempotent **by display
name** — an existing `C7NTAX Email Connector` registration is reused, consented again, and given a
further secret rather than a duplicate being created — and it returns the **Exchange Online** commands
that scope an app-only registration to one mailbox, because Graph has no route to those and an unscoped
app-only app can read every mailbox in the tenant. `POST /api/oauth-app/import` is the path for a
tenant this instance cannot reach Microsoft from: paste the script's JSON and the four values come back.
Everything is gated on `integration:manage`, and each deployment or import writes an audit row
(`entity: "oauth_app"`) naming the tenant, the client id and the secret's expiry — never the secret.

## 10. Outbound webhooks — C7NTAX telling you

The reverse direction exists too: register an endpoint and C7NTAX will POST to it when a monitored
service raises or resolves an alert.

| | |
|---|---|
| Register | `POST /api/alert-webhooks` (`url`, `secret`, `events`, `retryCount`, `isActive`) |
| Try it | `POST /api/alert-webhooks/{id}/test` — one attempt, right now, so the button can answer |
| History | `GET /api/alert-webhooks/deliveries` |
| Events | `service_alert.raised`, `service_alert.resolved` (plus `webhook.test`) |
| Flag | dispatching is behind the `monitoring` → `alertWebhooks` feature flag |

The body is a stable envelope:

```json
{
  "event": "service_alert.raised",
  "sentAt": "2026-10-08T02:14:51.205Z",
  "data": {
    "service": { "id": "…", "name": "Acme — M365", "category": "cloud" },
    "alert": {
      "id": "…", "title": "Elevated sign-in failures", "description": "…",
      "severity": "high", "status": "open", "source": "vendor-feed",
      "sourceUrl": "https://status.example.com/incidents/123",
      "detectedAt": "2026-10-08T02:10:00.000Z", "resolvedAt": null
    }
  }
}
```

Three headers come with it:

| Header | Meaning |
|---|---|
| `X-C7-Event` | the event name, same as the body's `event` |
| `X-C7-Delivery` | the delivery id, which is also the row in `GET /api/alert-webhooks/deliveries` |
| `X-C7-Signature` | `sha256=<hex HMAC-SHA256 of the raw body, keyed with the registration's secret>` |

**Verify the signature against the raw bytes**, before parsing:

```js
import { createHmac, timingSafeEqual } from "node:crypto";

const expected = `sha256=${createHmac("sha256", process.env.C7_WEBHOOK_SECRET).update(rawBody).digest("hex")}`;
const received = req.headers["x-c7-signature"] ?? "";
const ok = expected.length === received.length &&
  timingSafeEqual(Buffer.from(expected), Buffer.from(received));
```

```python
import hashlib, hmac
expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
ok = hmac.compare_digest(expected, request.headers.get("X-C7-Signature", ""))
```

Any non-2xx answer, or no answer within ten seconds, counts as an attempt; the delivery is retried
`retryCount` times with a 1s → 5s → 15s → 30s backoff and then recorded as failed with the reason
(`HTTP 500 from the endpoint`, a timeout, a refused URL). Delivery never blocks or fails the poll that
produced the event. **Answer `2xx` as soon as you have stored the body** — do your work afterwards.

## 11. Finding your way around

* **The specification** is the reference: `/api` is the prefix, and the server list in the document
  names both a deployment and local development.
* **`GET /api/api-keys/permissions`** returns every permission name and source kind that exists — build
  a key's scopes from that rather than from a hard-coded list.
* **`GET /api/health`** is the liveness check, unauthenticated.
* **`GET /api/system` / `GET /api/system/configs`** describe the deployment (version, feature flags,
  non-secret configuration). Reserved keys are withheld even from administrators, on purpose.
* **`GET /api/system/audit-logs`** (`user:manage` or `system:config`) is where to look when a change
  arrived and nobody admits to making it — API-key issuance and revocation are recorded there.

Permissions are named `resource:action` (`ticket:create`, `client:view`, `billing:manage`,
`user:manage`, `system:config`, `servicealert:manage`). A scope that names a permission nobody holds is
refused at issuance; a call whose credential lacks the required permission is `403`, and the document
carries `x-required-permissions` on every operation so you can tell before you try.

---

## 12. What integration work looks like, end to end

1. **Decide the direction.** If another system is telling you about an incident, use the event gateway
   (§7). If it is reading your data, or you are reading its, use a connector (§9). If you need to
   notify a third party, register a webhook (§10).
2. **Issue a key** on **Administration → API access** with the smallest scopes that work, named after
   the system and the tenant, and with an expiry if it has one.
3. **Send one event by hand** (`curl`) and read the answer — `created: true` means it opened a ticket;
   then send it again and confirm you get `merged: true` with `occurrences: 2`.
4. **Go live**, and check `GET /api/events/sources` a day later: a source with an `open` count and a
   recent `lastSeenAt` is a working integration.
5. **Write down the `externalId` rule** in your own runbook. It is the one decision that is hard to
   change later.

## 13. Keeping this true

The specification is generated from the routes, so it cannot drift *silently* — and the point of the
two scripts below is that it cannot drift *quietly* either.

```bash
node scripts/generate-openapi.mjs     # rewrite docs/openapi.yaml from the routes
node scripts/check-api-docs.mjs       # fail if the document and the application disagree
```

**The rule, for every change to the API surface:** when a route, its permission, its auth, or its
request/response shape changes, run the generator and — where the operation deserves prose a parser
cannot invent — add or update its entry in [`docs/api-operations.json`](./api-operations.json). Then
run the guard, and update this guide if it describes the thing you changed. The guard fails when the
document is behind the routes, when it describes an operation that no longer exists, or when a
curated summary names a route that has been renamed or removed.

Two honest notes about the document's edges:

* A router declared in a file but never mounted is **not** documented; the generator names it in its
  output instead, because a route nothing serves is not part of the API.
* Accessibility (`rolesRouter.get("/:id")` being reachable or not) is not something a generator can
  see: the mount point, the middleware and the permission name are, and those are what it records.
